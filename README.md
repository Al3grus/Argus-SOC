A home lab Security Operations Centre built on a cloud-hosted central platform and on-premise enterprise infrastructure. The lab is modelled on how a Managed Security Service Provider (MSSP) operates — a cloud SOC platform monitors a separate client enterprise network through an MSSP-deployed edge sensor — and demonstrates hands-on work across the security kill chain: network monitoring, threat detection, AI-powered alert triage, live endpoint forensics, incident response, and automated reporting.

> This is a home lab portfolio project. All attacks are executed against intentionally vulnerable services in a controlled lab environment. No real-world systems are tested.

Argus SOC is built around an **attack → gap → fix → re-test** pattern. Every red team scenario documents what the detection stack initially missed, the custom rules written to close the gap, and the re-test verification — including evidence of what the stack *failed* to detect on first run.

## 🏗️ Architecture — MSSP Topology

[![Argus SOC — Full Architecture Diagram](docs/assets/argus-soc-home-lab-architecture.sanitized.png)](docs/assets/argus-soc-home-lab-architecture.sanitized.png)
*Click to enlarge.*

The lab uses a three-tier architecture that mirrors how real MSSPs operate:

- **Central node — Cloud SOC Platform (cloud VPS)** — the central platform where all telemetry lands, alerts are processed, and the operator works.
- **Hypervisor — Client Enterprise Infrastructure (on-premise host running Proxmox)** — a small Active Directory enterprise: domain controller, domain-joined Windows 11 workstation, and intentionally vulnerable services. This is the monitored environment.
- **Edge sensor — MSSP Edge Sensor (on-site single-board computer)** — deployed at the client site, captures all network traffic via a hardware SPAN port on a managed switch, runs the NIDS and protocol analyser, and forwards logs to the central node.

The attacker (a Kali Linux VM) operates on the same subnet as the targets. The edge sensor sees every packet on the switch via SPAN, and the central node receives every alert generated by the edge.

## ⚡ The AI Detection Loop

Every Wazuh alert above threshold flows through an automated triage pipeline on the central node:

```
Traffic Capture (Suricata + Zeek on the edge sensor's SPAN interface)
       ↓
Detection Layer
  ├── Suricata: Signature matching (ET Open ruleset, 49,325 rules + custom rules)
  └── Zeek: Protocol metadata (conn.log, dns.log, http.log, ssl.log)
       ↓
Log Forwarding (Wazuh Agent on the edge sensor → Wazuh Manager on the central node, encrypted agent channel)
       ↓
SIEM Correlation (Wazuh: multi-source, MITRE ATT&CK mapping, custom rules)
       ↓
Webhook Trigger (Wazuh → n8n at level 3+, local-only webhook)
       ↓
AI Triage (Claude API: classify severity, MITRE tag, plain-English summary)
       ↓
Severity Routing (n8n Switch node)
    ├── Noise     → Silent log
    ├── Low       → Daily digest
    ├── Medium    → Telegram alert
    └── Critical  → Telegram + PagerDuty escalation
```

**Claude API output schema:**

```json
{
  "severity": "noise | low | medium | critical",
  "summary": "Plain-English explanation of what happened and why it matters",
  "mitre_technique": "T1190",
  "mitre_technique_name": "Exploit Public-Facing Application",
  "recommended_action": "respond_immediately",
  "confidence": 0.97,
  "reasoning": "Why this classification was chosen"
}
```

> In testing, Claude correctly classifies ~80% of ET Open rule hits as noise — transforming hundreds of daily raw alerts into ~20–40 actionable items, with critical events surfaced immediately.

## 🎯 Attack Scenarios — Detection Coverage

Five red team scenarios covering the kill chain. Each scenario follows the **attack → gap → fix → re-test** pattern.

| # | Scenario | MITRE Technique | Initial Detection | After Remediation |
|---|----------|-----------------|-------------------|-------------------|
| 1 | Reconnaissance (Nmap) | T1046 | Partial (protocol anomalies only) | ET SCAN firing — 199 hits |
| 2 | Credential Brute Force (Hydra) | T1110.001 | Full detection | N/A — full pipeline first time |
| 3 | Remote Code Execution (UnrealIRCd) | T1190 | Zero detection | 12 CRITICAL alerts after custom rules |
| 4 | Web Application Attacks (SQLmap) | T1190 | Zero detection | 33 alerts, SQLmap identified |
| 5 | Lateral Movement (pivot) | T1021 | Partial (Claude classified as LOW) | CRITICAL, T1021 mapped after rule update |

Active Directory-specific scenarios (Kerberoasting, AS-REP roasting, DCSync, lateral movement on Windows) are planned for Phase 6.

## 🔒 Security Notes

This repository documents the lab's architecture, detection logic and attack scenarios — not its live deployment.

- **Real addresses, hostnames and credentials are not in this repo.** Hosts are named by role (`central-01`, `sensor-01`, `hypervisor-01`) and addresses by placeholders such as `<LAB_SUBNET>`, `<WG_SUBNET>` and `<VPS_PUBLIC_IP>`.
- **Secrets come from the environment.** See [`.env.example`](.env.example); `.env` and real service configs (WireGuard, Wazuh, Cowrie, camera) are git-ignored.
- **Commits are scanned before they land.** A pre-commit hook ([`scripts/opsec_scan.py`](scripts/opsec_scan.py)) blocks private-range IPs, secrets and a local denylist of real values, including text embedded in diagram images. Enable it with `git config core.hooksPath .githooks`.
